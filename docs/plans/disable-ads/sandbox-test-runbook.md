# PayPal Sandbox Checkout — End-to-End Test Runbook

Purpose: prove the full purchase path works before switching either side to `live`.

Read §0 first — two constraints change what this test can and cannot prove.

---

## 0. What this test does and does not cover

**It runs against the real `streamflix-chat` Realtime Database.** The plan calls for
an emulator or a throwaway Firebase project; neither is available here, because the
Database emulator will not start on this machine (see the JVM `AF_UNIX` failure in
[deployment-notes.md §5](deployment-notes.md)). So a successful test writes real
records under `accounts/<your-uid>/adFree`, `adFreeKeys/`, and `adFreeOrders/`.
Consequences:

- Use **your own** Google account, not a real user's.
- The account you test with becomes permanently ad-free. `create-adfree-order`
  returns `409 already-ad-free` on every later attempt, so a second purchase test
  needs either a second Google account or a manual delete of
  `accounts/<uid>/adFree` from the Firebase console.
- Money is never real. PayPal sandbox balances are fake.

**Security rules are not part of this test.** The tightened `.write` rule and the
`adFreeKeys` / `adFreeOrders` locks are uncommitted local edits to
`database.rules.json` and have not been deployed or emulator-tested. You do not need
to deploy them to run this test: `accounts/$uid` already granted the owner `.read`
before this feature, so the client listener sees the entitlement under the rules
that are live right now. What that means is that this runbook verifies the
**purchase mechanics**, not the **write-lock**. Those 102 rules assertions stay
unverified until the emulator runs somewhere.

## 1. Prerequisites

### 1.1 Secrets — Cloudflare (Option A) or `.dev.vars` (Option B)

Six values must reach the Pages Functions runtime. Three are non-secret and come from
`wrangler.jsonc` `"vars"` (`FIREBASE_PROJECT_ID`, `FIREBASE_DATABASE_URL`,
`PAYPAL_CLIENT_ID`) — do **not** duplicate those anywhere else. The other three are
secrets, and **where you put them decides where you can test** (see §2):

| Secret | For the deployed site | For localhost |
|---|---|---|
| `AD_KEY_HMAC_SECRET` | Cloudflare → Secret | `.dev.vars` |
| `FIREBASE_SERVICE_ACCOUNT` | Cloudflare → Secret | `.dev.vars` |
| `PAYPAL_CLIENT_SECRET` | Cloudflare → Secret | `.dev.vars` |

The two sets are independent. Cloudflare secrets never reach localhost, and
`.dev.vars` is never uploaded. Filling one does nothing for the other.

`.dev.vars` already exists (gitignored) with `AD_KEY_HMAC_SECRET` generated. If you
are testing locally, fill the remaining two:

**`PAYPAL_CLIENT_SECRET`** — PayPal Developer Dashboard → Apps & Credentials →
**Sandbox** tab → your "Default Application" → click the 👁 / **Show** next to
Secret. This must be the sandbox secret paired with the sandbox client ID already
sitting in `wrangler.jsonc`. Mixing a live secret with a sandbox client ID fails at
the token step with an opaque `invalid_client`.

**`FIREBASE_SERVICE_ACCOUNT`** — Firebase Console → Project Settings → Service
Accounts → **Generate new private key**. That downloads a JSON file. `.dev.vars` is
dotenv-style and cannot hold multi-line JSON, so base64 it into one line:

```bash
node -e "console.log(require('fs').readFileSync('C:/path/to/serviceAccount.json','base64'))"
```

Paste the output after `FIREBASE_SERVICE_ACCOUNT=`. Delete the downloaded JSON when
you are done — it is an admin credential for the whole database.

If `AD_KEY_HMAC_SECRET` differs between Cloudflare and `.dev.vars` — which it does by
default, since the local one was freshly generated — keys generated in one
environment will not validate in the other. That is harmless for purchase testing and
only matters if you generate keys locally and try to redeem them on the deployed site.

`PAYPAL_ENV` stays unset. That is what selects sandbox on the server.
`VITE_PAYPAL_ENV` also stays unset, which selects sandbox in the browser. Both must
be unset (or both `live`) or the server and browser target different PayPal
environments and every order fails.

### 1.2 Create a PayPal sandbox buyer

PayPal Developer Dashboard → **Testing Tools** → **Sandbox Accounts**. There is
normally a pre-made `personal` account with an autogenerated
`sb-xxxxx@personal.example.com` address. Open its ⋮ menu → **View/Edit account** to
see or reset the password, and confirm it has a non-zero USD balance. You will type
these credentials into the checkout popup — do not use your real PayPal login.

### 1.3 Optional — admin key generation

To also test the in-app key generator in the same session, grant yourself the claim:

```bash
npm run chat:admin -- --uid <YOUR_FIREBASE_UID> --grant
```

Then sign out and back in — custom claims only land in a freshly minted ID token.

## 2. Where to run the test

There are two viable targets. Pick one — they need different setup from you.

### Option A (used on 2026-08-23): the deployed Pages site

Cloudflare's encrypted secrets exist **only** on the deployed site. They are one-way:
the Dashboard shows "Value encrypted" because Cloudflare cannot return them, to you
or to wrangler. So if your secrets live in Cloudflare and nowhere else, the deployed
site is the only place the flow can work.

```bash
npm run deploy
```

This is safe as a sandbox test **provided** neither `PAYPAL_ENV` (Pages env) nor
`VITE_PAYPAL_ENV` (build-time) is set to `live`. With both absent, server and browser
both resolve to sandbox. Verify after building:

```bash
grep -o 'VITE_PAYPAL_ENV[:=]"[^"]*"' dist/assets/index-*.js || echo "unset -> sandbox"
```

Confirm the functions deployed with an unauthenticated call — **`401` is the healthy
answer**:

```bash
curl -s -X POST https://streamflix.stream/api/create-adfree-order
```

Two costs to accept: the **Disable Ads** tab is visible to every signed-in visitor on
your public domain (they would get a sandbox order they cannot pay, so no money can
move), and with `database.rules.json` still undeployed a signed-in user could write
their own `accounts/<uid>/adFree` and self-grant ad-free.

> `wrangler pages deploy` can fail once with a bare `fetch failed` partway through.
> It is transient — rerun `npx wrangler pages deploy dist --commit-dirty=true` and it
> uploads normally.

### Option B: localhost

Requires `.dev.vars` filled in (see §1.1) — Cloudflare's secrets will not reach it.

```bash
npm run preview:pages
```

That is `vite build` then `wrangler pages dev dist --port 8788`. Wrangler prints
`Using vars defined in .dev.vars` and marks every binding `local`, which is the proof
that nothing comes from Cloudflare. Note `(hidden)` in that list means the key
*exists*, not that it has a value — an empty secret still shows as `(hidden)`.

`npm run dev` on `:5173` also works now: [vite.config.js](../../../vite.config.js)
proxies the four ad-free routes to `127.0.0.1:8788` ahead of the TMDB catch-all, so
you keep HMR. Wrangler must be running too, since Vite only forwards. If it is not,
you get an explicit `pages-functions-unavailable` error rather than a mystery 500.

Before that proxy existed, `/api/*` fell through to `https://api.themoviedb.org/3`
and a purchase click actually sent `POST api.themoviedb.org/3/create-adfree-order`,
answered with TMDB's `{"success":false,"status_code":34,...}`. If you ever see
`status_code: 34` from an ad-free route, the request left your machine for TMDB.

## 3. Walk the flow

Sign in with Google, then open **Settings → Disable Ads**. You should see the $2.99
upgrade card. Keep DevTools open on the Network tab.

Substitute your chosen origin below: `https://streamflix.stream` for Option A, or
`http://localhost:8788` (or `:5173`) for Option B.

### Stage 1 — order creation

Click **Purchase Ad-Free ($2.99)**.

| Check | Expected |
|---|---|
| `POST /api/create-adfree-order` | `200` with `{"ok":true,"orderId":"..."}` — a ~17-char uppercase alphanumeric id |
| Popup opens | URL is `https://www.sandbox.paypal.com/checkoutnow?token=<orderId>` — confirm the **sandbox** host |
| Button state | "Connecting to PayPal..." |

Failure modes worth recognising:

- `503 entitlement-check-unavailable` → `FIREBASE_SERVICE_ACCOUNT` is wrong,
  truncated, or has no RTDB access.
- `500` with `PayPal create order failed: HTTP 401` → `PAYPAL_CLIENT_SECRET` does
  not match the sandbox client ID.
- `409 already-ad-free` → this account is already entitled from an earlier run.
- No popup at all → the browser blocked it and the tab redirected instead; that
  fallback path works but you lose the auto-capture, so allow popups for localhost.

### Stage 2 — pay in the sandbox popup

Log into the popup with the sandbox **buyer** credentials. The order is created with
`shipping_preference: NO_SHIPPING` and `user_action: PAY_NOW`, so the popup should show
**no shipping address** and a **Pay Now** button. Approve the $2.99 payment.

> **If you instead see "Ship to \<name\> \<address\>" and a "Continue to Review Order"
> button that reloads the same step forever, the order was created without
> `application_context`.** PayPal then defaults `shipping_preference` to `GET_FROM_FILE`,
> treats the entitlement as a shippable good, and routes the click through its
> shipping-callback path, which spins and returns you to the same screen. The console
> shows `useShippingCallbackSpinner.ts` and `ShipTo.js` frames. Fixed on 2026-08-23 in
> [functions/lib/paypal.js](../../../functions/lib/paypal.js); if it recurs, that block
> was lost. Nothing in the popup reports this as an error.

> **The popup will not close by itself.** The order still sets no `return_url`, so
> PayPal has nowhere to send the buyer and parks them on its own confirmation page.
> The frontend polls `popup.closed` once a second and does nothing until then.
> **Close the popup manually.** This is expected behaviour, not a hang — but it is
> worth deciding later whether you want an `application_context.return_url` so the
> flow closes itself in production.

### Stage 3 — capture and activation

The moment you close the popup:

| Check | Expected |
|---|---|
| `POST /api/purchase-adfree` | `200` with `{"ok":true,"activatedAt":<ms>}` |
| Request body | `{"orderId":"...","requestId":"adfree-<orderId>"}` — the requestId must be present and derived from the order |
| Toast | "Payment verified! Lifetime Ad-Free is now active." |
| Settings pane | flips to **Lifetime Ad-Free Active**, method "PayPal Purchase ($2.99)", showing your email and the order id |

### Stage 4 — database state

Firebase Console → Realtime Database. Three records must exist:

```
accounts/<your-uid>/adFree
  keyHash      64 lowercase hex chars
  activatedAt  epoch ms
  method       "purchase"
  orderId      <orderId>

adFreeKeys/<keyHash>
  status       "redeemed"

adFreeOrders/<orderId>
  status       "completed"
```

`adFreeOrders/<orderId>` passing through `reserved` → `captured` → `completed` is the
state machine working. If it is stuck on `reserved`, capture never returned; if
`captured` but not `completed`, the entitlement write failed after PayPal already
took the money — that is the case the resume path exists for, and re-clicking
purchase should finish it.

### Stage 5 — the ad gate

In the DevTools console:

```js
window.__STREAMFLIX_AD_STATE
```

Expect `"adfree"`. Reload and check it again — it should go `"pending"` briefly and
then `"adfree"`, never `"ads"`. Then load a watch page and confirm no popunder
fires and no ad containers render.

### Stage 6 — retry safety

Worth doing explicitly, since it is the part that protects real money. With the
account now ad-free, click purchase again: expect `409 already-ad-free` from
`create-adfree-order`, and no second charge in the sandbox account's transaction
history. PayPal sandbox → Testing Tools → Sandbox Accounts → your buyer → should
show exactly **one** $2.99 payment.

## 4. Switching to live — do not do this until §3 is fully green

Four things change together:

1. PayPal Dashboard → **Live** tab → create/locate the live app. Its client ID and
   secret are entirely separate values from the sandbox pair.
2. `wrangler.jsonc` `vars.PAYPAL_CLIENT_ID` → the **live** client ID.
3. Cloudflare Pages → Settings → Variables and secrets:
   `PAYPAL_CLIENT_SECRET` (Secret) → the live secret, and `PAYPAL_ENV` (Variable)
   → exactly `live`. Not `production`, not `LIVE` — anything else silently means
   sandbox.
4. `VITE_PAYPAL_ENV=live` at build time, then **rebuild**. It is a Vite variable
   baked into the bundle, so a redeploy without a rebuild leaves the browser
   pointing at sandbox while the server creates live orders.

Also still outstanding before a real launch: get `npm run test:rules` and
`npm run test:rules:transitional` green on a machine with a working Database
emulator, then deploy `database.rules.json`. Until those rules are live, a
determined client can write its own `accounts/<uid>/adFree` record directly.
