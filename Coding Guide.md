Think Through Problems
1. Research Before Action
I never jump straight into writing code. I first:

Explore the project structure to understand the architecture
Read existing code patterns, conventions, and style
Check dependencies, configs, and build systems
Identify what already exists to avoid reinventing the wheel
2. Plan with Precision
For complex tasks, I create a structured implementation plan:

Break the problem into components ordered by dependency
Identify which files need to change and why
Flag risks, open questions, and design decisions upfront
Get alignment before writing a single line
3. Execute Methodically
Work through a task checklist, marking progress
Make targeted edits — not wholesale rewrites
Preserve existing comments, patterns, and conventions
Handle edge cases as I go, not as an afterthought
4. Verify Ruthlessly
Run builds, tests, and linters after changes
Check the actual output in the browser/terminal
Trace errors back to root causes instead of patching symptoms

What Makes the Approach Work
Principle	Why It Matters
Context-first	Understanding the codebase prevents fighting existing patterns
Incremental changes	Small, focused edits are easier to debug than big rewrites
Tool leverage	Grep, file search, and semantic search find answers faster than guessing
Thinking out loud	The extended thinking step lets me reason through complex logic before committing
Pattern recognition	I identify recurring idioms in your codebase and stay consistent
Error-driven learning	When something breaks, I read the full error, trace the stack, and fix the root cause

The "Thinking" Advantage
The extended thinking capability means I can:

Reason through multi-step logic before writing code (like tracing data flow across files)
Weigh tradeoffs between approaches silently before proposing one
Catch my own mistakes during the reasoning phase, not after the edit
Hold complex state — like understanding how 5+ files interact in a single change

The Honest Truth
There's no magic — it's disciplined process:

Understand → don't assume
Plan → don't improvise on complex tasks
Execute precisely → don't over-edit
